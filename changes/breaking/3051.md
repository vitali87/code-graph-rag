With `CGR_VECTOR_STORE_BACKEND=qdrant` and neither `QDRANT_URL` nor `QDRANT_DB_PATH` set, the Qdrant of the `cgr daemon up` stack now takes the embeddings only of a graph that lives in the stack's own Memgraph: `GRAPH_BACKEND=memgraph`, with `MEMGRAPH_HOST` and `MEMGRAPH_PORT` reaching the stack's Memgraph. An embedded (`sqlite`) or Neo4j graph, or another Memgraph, no longer picks it up automatically, and `cgr start` no longer starts the stack's Qdrant for an embedded or Neo4j graph. Such a graph mixed its vectors into the stack graph's collection, and its `cgr start --clean` deleted that whole collection. The log says when the stack's Qdrant is passed over, and why.

To keep the old behaviour, set `QDRANT_URL` to the stack's Qdrant (by default `http://127.0.0.1:6333`; `CGR_STACK_BIND_HOST` and `QDRANT_HTTP_PORT` change it). `cgr start` then starts it and writes to it as before, whatever the graph engine.

Existing installs: vectors already in the stack's Qdrant stay there, and a graph in the stack's own Memgraph keeps using them. With the embedded graph, Neo4j or another Memgraph, new runs write to the embedded Qdrant store in `./.qdrant_code_embeddings` unless `QDRANT_URL` is set, and semantic search no longer finds the vectors in the stack's Qdrant. See [Semantic Search](https://docs.code-graph-rag.com/sdk/semantic-search/).
